## 3. 为什么做

系统 WebView 版本碎片化会影响阅读视图注入、抽图与后续拦截行为。经红色审批后，产品改为自带较新 Chromium 内核，并保证阶段 C 的拦截类能力在选型时就可验证，避免引擎定死后无法实现净化目标。

## 4. 本次范围

- 决策基线、会话交接与需求纪要写明：捆绑 Chromium、B2、L1、仅 arm64-v8a、无体积上限；
- 写明广告资源拦截、跳转中页跳过为内核/SDK **选型与验收硬条件**；
- 记录红色批准转述，供后续浏览器 Spec 引用。

明确不做：

- 不写入 iOS 皮肤或整套 HIG 移植。

## 5. 用户如何使用

本次为文档边界变更，无终端用户操作流。后续阶段 A/B/C 实现时，用户将使用携带自有 Chromium 内核的 App（仅 64 位 ARM 设备）。

## 6. 产品规则

- 当记录内核策略时，系统（文档）必须写明：采用可嵌入 Android 的现成 Chromium 系 SDK/库（B2），而非自编译整棵 Chromium 树（B1）。
- 当记录版本策略时，必须写明：尽量跟随当时 Chromium/Chrome Stable（L1）。
- 当记录 ABI 时，必须写明：仅 arm64-v8a；不承诺 32 位或 x86。
- 当记录体积时，必须写明：无体积上限（接受包体显著增大）。
- 当记录净化能力时，必须写明：广告资源拦截与跳转中页跳过为 SDK 选型硬条件；候选不过关则换 SDK，不得用「已内置 Chromium」代替功能验收。
- 系统不得把「仍默认仅用系统 WebView、永不捆绑」写为当前有效产品边界（宪章原文保留「须红色审批」表述，本次批准即该路径的生效结论）。
