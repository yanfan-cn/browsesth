# ClearPage 项目开发宪章

> 本宪章是 ClearPage 项目唯一不可由 AO 自行修改的文件。它规定开发方向、技术边界和质量底线。具体需求、方案与实施记录分别放在 `docs/`、Spec、Plan 和 Log 中。
>
> **工作名说明：** 仓库与产品暂用名 `ClearPage`（清页）。所有者可随时更名，更名后须同步本文件标题与 `docs/` 中的产品名，不改变宪章其余约束效力。

## 1. 适用对象与权威顺序

本宪章适用于所有开发人员和执行任务的 Agent。**任务下达者**指当前聊天中向 Agent 提出任务、回答问题并决定是否确认开工的人。

发生冲突时，按以下顺序处理：

1. 本宪章；
2. `docs/产品与开发决策基线.md`；
3. 当前功能 Spec；
4. 当前功能 Plan；
5. Spec 明确引用的其他 `docs/` 材料；
6. 现有代码、测试和历史 Log。

AO 必须主动消除冲突，不能挑选最方便的一份执行。只有项目所有者可以修改宪章；宪章以外的仓库文件均由 AO 在职责范围内自主维护。

## 2. 项目使命与产品边界

- **项目使命：** 在 Android 上提供内置浏览器与「阅读视图」，让用户在小说站与漫画站获得去广告、少跳转的清爽阅读体验；小说与漫画同等重要。
- **主要用户：** 希望用手机干净地阅读网络小说与漫画、不愿维护书源规则的个人用户。
- **技术底座：** 以开源项目 Legado with MD3（阅读）为代码起点进行产品改造，而非从零重写全部基础设施。
- **核心交付：**
  - 内置浏览器（基于系统 WebView，非捆绑完整 Chromium）；
  - 类 Safari 阅读视图：抽取小说正文，弱化广告与干扰元素；
  - 漫画：从网页抽取图片列表，进入专用漫画阅读器（优先复用 Legado 漫画阅读器能力）；
  - 书签、历史与基础阅读会话管理。
- **明确不做（当前边界）：**
  - 不提供、不维护「书源 / 漫画源」规则解析作为产品主路径（可在过渡期隐藏或逐步下线，不得作为新功能主入口）；
  - 不整包移植 Cimoc 图源解析与 Fresco 阅读器栈；仅允许移植可独立验证的算法（如白边裁剪）；
  - 默认不捆绑完整 Chromium 引擎（体积与维护成本过高）；若将来要捆绑，须走红色问题审批；
  - 不做内容托管、不预置第三方站点内容、不做公网多租户内容分发。
- **运行环境：** Android 手机与平板；目标系统版本与 WebView 兼容策略在决策基线与阶段 Spec 中细化。
- **质量底线：**
  - 浏览器主路径可打开常见 HTTP(S) 站点；阅读视图与抽图失败时须可回退到普通网页浏览；
  - 关键 WebView 版本差异须检测并降级，不得静默白屏视为成功；
  - P0 崩溃与隐私泄露为零；不收集阅读正文上传到开发者服务器（除非用户明确开启且已批准的同步能力）。

### 2.1 阶段划分（可调整优先级，不可偏离边界）

- **阶段 A（浏览器 + 小说阅读视图 MVP）：** 地址栏/导航、历史与书签；进入阅读视图可抽取常见文章型小说页正文；失败可退出回网页。
- **阶段 B（漫画抽图 + 漫画阅读器）：** 从当前页或会话抽取图片 URL 列表；接入 Legado 风格漫画阅读器（分页/条漫等）；小说与漫画入口对等。
- **阶段 C（净化增强）：** 广告资源拦截、常见跳转中页识别与跳过、阅读进度与会话整理；可选白边裁剪等阅读增强。

AO 可以自主拆分阶段内任务与实现路径，但最终结果不得偏离以上边界。

## 3. 核心开发原则

### 3.1 先定义结果，再开始实现

任何功能或修复都必须先形成精简 Spec，说明用户问题、范围、产品规则和验收标准。代码、静态页面、Mock、TODO 或口头宣称都不能代替产品合同。

### 3.2 单一事实来源

同一事实只在最合适的位置完整描述：

- `docs/`：项目背景、长期方向、原始需求和决策依据；
- Spec：当前功能要实现什么；
- Plan：当前功能准备怎样实现和验证；
- Log：实施过程中实际发生了什么；
- 代码与测试：当前可运行行为。

其他文件通过链接和 ID 引用，不复制大段内容。发现事实过期时，AO 直接更新对应事实来源及受影响引用。

### 3.3 需求必须可验证

“支持、优化、体验良好、尽量准确、基本完成”等表述不能直接作为验收标准。每条验收标准必须写清前提、操作和可观察结果。

### 3.4 全链路可追溯

每项开发都应能够沿以下链路回溯：

```text
需求依据 -> SPEC/AC -> PLAN/TC -> 代码改动 -> LOG/证据 -> Commit
```

不再维护独立 Traceability 文档，追溯关系直接记录在 Spec、Plan 和 Log 中。

### 3.5 最小范围、完整结果

AO 不做与当前目标无关的顺手重构，但必须完成本功能不可缺少的测试、错误处理、安全修复和文档同步。最小范围不等于只修演示路径。

### 3.6 兼容优先、渐进演进

优先复用 Legado with MD3 已验证能力（尤其是漫画阅读器、WebView 工具链、存储与主题），避免无必要重写。需要迁移时先定义兼容、回退和数据保护方式。

### 3.7 数据契约先行

涉及接口、文件、数据库、模型输出或跨模块状态时，Plan 必须先定义输入、输出、必填项、错误、生命周期和兼容规则，再开始实现。

### 3.8 测试和证据优先

先决定如何证明正确，再写实现。严格区分：

- 代码存在；
- 可以编译或启动；
- 功能可以运行；
- 功能经过有效测试；
- 功能满足 Spec 验收标准。

没有证据就标记“未验证”，不能推测为通过。

### 3.9 安全和隐私默认保护

密钥、令牌、个人信息、敏感业务数据不得进入源码、提交、截图或 Log。外部输入默认不可信，必须根据风险进行校验、限制和隔离。

### 3.10 文档与实现同步

需求变化先更新 Spec，方案变化先更新 Plan，实施事实持续写入 Log。不得代码先行后再修改文档，使文档看起来像原计划。

### 3.11 零静默问题

AO 发现会影响产品结果、技术方向、安全、数据或验收的不确定性时，必须在聊天框主动暴露，不能只写入文档、风险表、TODO 或 Log 后继续。

问题应在一次调查后集中提出，避免能一起确认的问题被拆成多轮零散提问。

### 3.12 开工前需求复述与确认硬门禁

每次任务开工前，Agent 必须先只读调查并解决所有影响需求理解的问题。问题全部解决后，Agent 必须在聊天框使用简洁、明确的自然语言完整复述最终需求。只有任务下达者针对该次复述明确回复“确认”后，Agent 才能进入 `Spec → Plan → 实施 → Log → 验证交付`。

确认前，Agent 只能只读调查、提问和复述，不得创建或修改任何项目文件。已有文档、历史确认或 Agent 自身判断不能代替本次确认。确认后如需求、范围、保留行为、禁止事项或验收要求变化，原确认立即失效，Agent 必须重新复述并再次取得“确认”。

提问和复述必须优先使用面向用户结果的非技术语言。技术术语不可避免时，必须同时解释它会让用户、维护、成本或风险发生什么变化。能从仓库、文档或运行证据查明的事实由 Agent 自行调查。

### 3.13 红色问题与上级批准

以下六类属于红色问题，当前开发人员不能自行批准：

1. **产品定位和范围**：改变目标用户、核心场景、核心功能、阶段范围，或重新引入书源主路径、捆绑 Chromium、公网账号体系等边界变化。
2. **核心用户行为**：重做整体信息架构、删除主要入口、改变核心主流程或重要内容默认可见性。
3. **技术架构**：迁移核心框架，引入不兼容数据格式，改变部署平台，或锁定长期技术方向（如强制内嵌 Chromium、整包合并 Cimoc）。
4. **数据、安全和隐私**：收集或持久化用户数据到开发者服务器，删除/迁移/不可逆修改数据，改变安全边界。
5. **外部影响和成本**：对外发布、真实付费、联系第三方、使用授权不明素材、显著增加持续费用。
6. **验收和承诺**：降低验收标准，接受 P0/P1 缺陷，将未验证视为可接受。

出现红色问题时，AO 必须暂停并提供上级决策包：问题与现状、需要上级决定的原因、2～4 个互斥方案、用户/成本/风险影响、推荐及待确认结论。

只有当前开发人员明确转述上级批准，并说明批准方案、范围和限制后才能继续。Log 记录日期及“由当前操作者转述”。

## 4. 技术栈与技术边界

本节是 AO 选择方案时的硬边界。能用现有 Legado 能力满足批准功能时，先改造、模块化和补测试，不因偏好整体重写。

### 4.1 核心技术栈

| 层级 | 允许使用 | 当前入口或位置 | 约束 |
| --- | --- | --- | --- |
| 语言/平台 | Kotlin；Android | 后续 `app/`（自 Legado 派生） | 不以 Java 旧栈（如 Cimoc MVP）作为新主路径 |
| UI | Jetpack Compose + 必要 View/WebView 互通；Material 3 为默认视觉 | 后续 UI 模块 | 不强制整 App iOS 皮肤；若做 Cupertino 风格须单独 Spec |
| 浏览器内核 | Android 系统 `WebView`；Accompanist/官方 WebView 封装 | 浏览器 feature | 默认不捆绑 CEF/完整 Chromium；须有版本检测与降级 |
| 阅读视图 | 本地 HTML 解析 / Readability 类算法 / 可控 JS 注入 | 浏览器/阅读 feature | 失败必须可回退网页；不得假设全站通用 |
| 漫画阅读 | Legado `ui/book/manga` 能力与会话模型 | 漫画 feature | 图片来源改为网页抽取，不接入 Cimoc 硬编码图源 |
| 网络 | OkHttp 等现有栈；WebView 请求拦截（按需） | help/http、WebViewClient | 拦截规则可配置；默认不上传用户浏览正文 |
| 存储 | 本地 DB/文件（书签、历史、会话、图片缓存） | data/ | 首批不做强制云账号；WebDAV 等同步属后期可选 |
| 测试 | 单元测试、仪器测试、真机人工验收 | `app` 测试目录 | 阅读视图与抽图须有样例页或录屏证据 |
| 参考代码（只读） | `legado-with-MD3`、可选 `Cimoc` 算法参考 | `D:\cursor\` 旁系仓库 | 参考不等于依赖；合入须许可证与 Plan 说明 |

### 4.2 技术选择原则

- 当前技术栈能够满足功能、质量和部署目标时，不因偏好而重写。
- 新依赖必须有明确用途，优先选择维护活跃、许可清楚、体积和运行成本可接受的方案。
- AO 可以自主增加、升级或移除普通依赖，但必须在 Plan 中记录理由、兼容影响和验证方式。
- 核心框架或数据方案确需改变时，必须先在聊天框向操作者说明原因、迁移影响和回退方案，获得确认（红色问题另走 3.13）。
- 所有外部站点访问必须提供超时、失败反馈和可接受的降级路径（至少退回普通 WebView）。

### 4.3 代码结构约束

仓库初期以 SDD 与产品文档启动；引入 Legado 派生代码后按下表收敛：

| 目录/模块 | 职责 | 禁止内容 |
| --- | --- | --- |
| `specs/` | 宪章、Spec、Plan、Log | 密钥、用户隐私快照、不可复核的“已完成”空话 |
| `docs/` | 产品决策、需求纪要、合规说明 | 用文档代替运行证据 |
| `app/`（后续） | Android 应用主模块 | 硬编码第三方站点完整爬虫规则作为主产品能力 |
| 浏览器 feature（后续） | 导航、历史、书签、阅读视图、抽图入口 | 与漫画渲染强耦合的单体上帝类 |
| 漫画 feature（后续） | 图片会话、阅读器 UI | 重新引入 Cimoc Fresco 双栈并行作为默认 |
| 书源相关遗留（过渡） | 仅兼容/迁移/删除 | 不得作为新功能默认入口 |

通用要求：入口保持清晰；业务规则不散落在 UI；密钥不写入客户端；Mock 与真实数据明确分离。

## 5. 精简 SDD 工作区

每个功能只使用三份工作文档：

```text
specs/features/SPEC-XXX.md   产品合同
specs/plans/PLAN-XXX.md      工程方案与执行步骤
specs/logs/LOG-XXX.md        实施事实与验证证据
```

不单独建立 Requirement、Traceability、Task 或 Review 文档：

- 原始需求保存在 `docs/`；
- Task 作为 Plan 内的可验证执行步骤；
- 追溯关系写在三份文档的链接和 AC/TC 中；
- Review 发现的修复仍使用一组精简 Spec、Plan 和 Log。

小改动可以缩短三份文档，但不能删除目标、边界、执行方案、验证标准和事实日志。

### 5.1 强制文件生成与执行顺序

AO 或其操作的 Agent 收到任何需要修改项目文件的开发请求后，必须自动完成以下动作，不等待操作者额外提醒：

```text
读取宪章与相关需求
  ↓
只读调查并解决需求疑问
  ↓
简洁完整复述需求，等待任务下达者回复“确认”
  ↓
创建或更新 Ready 的 SPEC-XXX.md
  ↓
创建或更新对应 PLAN-XXX.md
  ↓
严格按照 Plan 开始修改代码、测试、配置或资源
  ↓
创建并持续回填对应 LOG-XXX.md
  ↓
执行验证、补齐证据、交付上级验收
```

强制门禁：

1. **确认门禁**：任务下达者未针对 Agent 本次完整复述明确回复“确认”时，只能只读调查、提问和复述，禁止创建或修改任何项目文件；红色问题没有具体上级批准时同样禁止开工；
2. **Spec 门禁**：不存在当前工作的 Ready Spec 时，禁止创建实施性 Plan、修改产品文件或宣称开工；
3. **Plan 门禁**：Spec 已存在但没有对应 Plan 时，禁止修改代码、测试、配置、数据、资源或部署文件；
4. **实施门禁**：只能执行 Plan 已列明的步骤；出现必要偏差时先更新 Plan，再继续修改；
5. **Log 门禁**：完成实施后必须创建或更新对应 Log，如实回填实际改动、命令、成功与失败、偏差和未验证项；
6. **交付门禁**：Log 未包含 AC/TC 证据、失败记录、未验证项和最终结果时，禁止宣称完成或提交验收。

Agent 每次恢复中断工作时，必须先读取当前 Spec、Plan、Log，判断自己处于哪一道门禁之后，再执行下一步。不得因为代码中已有半成品而跳过文档链。

执行顺序必须能够从工具调用记录、文件时间或内容证据中验证为：`Spec 创建/更新 ≤ Plan 创建/更新 ≤ 首次产品文件修改 ≤ Log 最终回填`。如果无法证明 Spec 和 Plan 先于开工，流程验收视为失败，即使最终功能测试通过也不能声称遵守 SDD。

仅以下操作不强制生成三份文件：纯只读调查、回答问题、查看状态，以及明确不产生仓库变更的审计。只读调查一旦转为修改，必须立即进入上述流程。

### 5.2 弱模型防错规则

- 操作者只需描述目标，不需要额外命令 Agent 创建 Spec、Plan 或 Log；Agent 必须自动识别并创建；
- 文件统一使用同一编号，例如 `SPEC-012`、`PLAN-012`、`LOG-012`；
- Agent 应在实施过程中保留命令和结果，完成后立即回填 Log；
- Agent 每进入下一阶段前，必须在聊天框用一句话报告“已完成哪道门禁，下一步做什么”；
- 缺少模板时，Agent 应按宪章最小字段创建文件，不能以模板缺失为由直接写代码；
- 任务很小时可以缩短内容，但不能合并或省略三份文件；
- 每个任务都必须按第 6.2 节完成需求复述并取得“确认”；
- 红色问题必须生成决策包并等待具体上级批准。

## 6. 标准开发流程

### 6.1 调查与建立 Spec

Agent 先阅读宪章和最相关的 `docs/`，再检查真实代码。无论是否存在已批准文档，都必须先完成第 6.2 节确认，再根据已确认事实建立功能 Spec。

### 6.2 开工前需求复述与确认

对每个任务，Agent 在创建或修改 Spec 前必须：

1. 先尽可能调查仓库，排除能从事实得到答案的问题；
2. 有疑问时用通俗语言集中提问，让任务下达者纠正或补充；
3. 一次性整理已发现的问题；
4. 说明不同选择会让用户看到什么变化；
5. 给出互斥选项、推荐及理由；
6. 执行六类红色问题检查；
7. 问题解决后简洁完整复述最终需求，并请任务下达者回复“确认”；
8. 只有收到针对该次复述的“确认”后，才能创建或更新 Spec 并继续。

聊天记录是确认入口，文档只记录确认后的结论。

### 6.3 调查代码与建立 Plan

AO 根据已确定的 Spec 调查当前入口、调用链、可复用模块、测试和部署条件，然后自主形成 Plan。Plan 至少包含现状证据、唯一方案、改动范围、数据合同、可验证步骤、测试与回退。

### 6.4 开工基线

写代码前必须记录：当前分支和提交、`git status`、相关测试或启动基线、缺失依赖/设备、无法验证事项。

### 6.5 小步实施

按 Plan 可验证步骤推进；失败先定位根因；超出范围先更新 Spec/Plan；不得伪造完成。

### 6.6 自我 Review

覆盖 AC、回归、错误反馈、安全、有效测试、文档一致、Diff 干净。

### 6.7 Log、提交与交付

Log 持续追加；完成后补齐证据并交付验收。上级只验收成果。

## 7. AO 权限与责任

### 7.1 AO 可以自主执行

除宪章外，AO 有权维护 `docs/`、Spec、Plan、Log、产品代码、测试、配置与依赖（非红色范围内）。

### 7.2 必须通过聊天框暴露

产品目标歧义、技术方向重大变化、数据安全边界、付费/密钥/发布、资料冲突、无法达标需改目标等情况，必须在聊天框集中说明并确认。红色问题须上级决策包。

### 7.3 禁止行为

- 修改或绕过本宪章；
- 隐藏问题、伪造证据；
- 泄露密钥或敏感数据；
- 覆盖无关用户改动；
- 未确认目标就实施会产生不同产品结果的猜测；
- 未验证就宣称通过；
- 擅自对外发布或扩大外部影响。

## 8. 测试与质量门禁

### 8.1 最低验证

每个 Plan 必须写出实际命令，至少覆盖适用项：编译、Lint/类型、单元测试、集成测试、主流程真机验证、构建产物检查。

### 8.2 有效测试标准

测试必须有能失败的有效断言。空测试、只调用不判断、固定 Mock 自证、被跳过或从未运行的测试不能作为完成证据。

### 8.3 完成定义

Spec AC 有证据；Plan 检查已执行；正常/失败/边界与回归已覆盖；无未处理 P0/P1；安全满足；文档同步；Log 完整；提交可回退（或明确说明未用 Git）。

### 8.4 ClearPage 阶段门禁

**阶段 A 完成须同时满足：**

- 可打开 HTTPS 网页并完成前进/后退/刷新/书签或历史之一；
- 对至少 2 类约定样例小说页，阅读视图能抽出可读正文；失败有明确提示且可回退网页；
- WebView 过旧时有检测提示或降级说明，不得伪造成功。

**阶段 B 完成须同时满足：**

- 对至少 2 类约定样例漫画页，能抽出有序图片列表并进入漫画阅读器；
- 分页与条漫至少一种模式可验收；加载失败可重试或返回浏览器；
- 小说与漫画入口在主导航中对等可见。

**阶段 C 完成须同时满足：**

- 至少一种广告拦截或跳转中页跳过策略有可重复样例证据；
- 阅读会话/进度行为有 Spec 级验收；
- 未完成项如实列入 Log，不得用“基本净化”代替。

## 9. 安全、隐私与外部能力

- 仓库只保留无真实值的配置模板。
- 日志最少信息：默认不记录完整 URL 参数中的令牌、Cookie、正文全文。
- 用户浏览内容默认仅存本地；任何上传/同步须单独 Spec 与确认。
- 应用不预置侵权内容；用户自行访问第三方站点的合规责任须在产品说明中声明（参见决策基线）。
- WebView/JS 桥暴露面最小化；`addJavascriptInterface` 仅用于必要白名单 API。

## 10. Git 与工作区纪律

- 开工前检查分支、提交和 `git status`。
- 不使用 `reset --hard`、强制覆盖或不明确目标的递归删除。
- 发现脏工作区时保留无关改动。
- 一个提交表达一个可说明、可测试、可回退的结果。
- 建议格式：`类型(范围): 结果`，例如 `feat(reader): add readability entry`。
- 推送、合并、发布除非操作者明确授权，否则不得执行。

## 11. 变更、修复与例外

### 11.1 需求与方案变化

需求变化时立即暂停，重新复述并取得“确认”，再更新 Spec/Plan 后继续。

### 11.2 缺陷修复

仍走精简 Spec、Plan、Log；可缩短但不可省略预期行为、回归与证据。

### 11.3 紧急情况

可先止血，随后立即补齐最小文档与验证。

## 12. 上级验收方式
