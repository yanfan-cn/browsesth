## 取证（2026-10-19 10:35，真机 vivo V2157A 实测）

- 截图 + `wm size/density`（1080x2400 @480dpi）+ uiautomator bounds：顶栏行 32→86dp（`NtpTopBarHeight` 本已 54dp），内容卡顶 122dp（safeDrawing 32 + `NtpContentShiftDown` 90）→ 空隙 36dp = 操作者所指空白。
- 操作者选 B：顶栏行保持 54dp、缩小空隙；其余组件相对位置不变。

## 实施（2026-10-19）

- `BrowserUiTokens.NtpContentShiftDown`：90dp → **66dp**（= 顶栏 54 + 12 间距）。单 token，横屏/平板分支不受影响。
- 组装 **1.4.2-beta**（code 184）成功（133s），props 进位 **1.4.3/185**。
- 装机：11:02 操作者确认后 `pm install` **Success**，`versionName=1.4.2-beta`。
- **AC-01 目测通过**（真机截图）：内容列顶 ≈97dp，顶栏行底 86dp，空隙 ≈12dp（原 36dp）；搜索/快捷/阅读列表/资讯布局正常。
- AC-02（横屏/平板/无痕）：待抽验。

## 修订（2026-10-19 11:11，操作者反馈回退）

- 操作者反馈：装机后「浏览器主页的 NTP 组件位置发生变化，不是说了只改顶栏吗？」——B 方案的 90→66 实际把整个内容列（搜索胶囊/快捷/阅读列表/资讯）整体上移 24dp，违背「其他组件位置不变」的约束；此前 10:35 取证截图为 NTP 处于滚动恢复状态，内容卡顶 122dp 的测量不代表未滚动时的自然位，导致误诊。
- **回退**：`BrowserUiTokens.NtpContentShiftDown` 66dp → **90dp**（组件位置完全恢复 1.4.1 状态）。顶栏行 54dp 本就生效，SPEC-140 的「顶栏 54dp」目标无需代码改动即已满足。
- 后续：如操作者仍指认顶栏区域空白，需其提供标注截图（明确「顶栏」所指区域与期望高度）再立新方案，不再盲改 token。

## 修订 R3（2026-10-19 11:59–12:10，操作者明确间距）

- 实测澄清（uiautomator）：图标行本身 32→86dp（=54dp 无误），操作者所指「顶栏不是 54dp」= 图标行与搜索框之间 ≈38dp 空白带（86→124dp）。
- 操作者定案：删除该空白带语义下，**图标行底与搜索框间距 = 135dp**（其余内容列随之下移）。
- 实施：`NtpContentShiftDown` 90 → **187dp**（32 + 187 + 2 卡片内边距 = 搜索框顶 221dp = 86 + 135）。图标行/状态栏不动。
- 组装 **1.4.5-beta**（code 187）成功；装机 Success（12:08，versionName 确认）。
- uiautomator 复测：搜索胶囊图标顶 229px→687px（229dp 处图标 / 卡片顶 221dp）= 间距精确 135dp；快捷/阅读列表/资讯同步下移（资讯头 ≈718dp，近屏底，可滚动）。
- 里程表现为 **1.4.6 / 188**（本轮 assemble 误进位已按交接规则处理）。

## 修订 R4（2026-10-19 12:09–12:15，操作者否定 R3）

- R3 把操作者「间距135dp」误读为「图标行与搜索框间空 135dp」，搜索框被推到 221dp（屏幕近 1/3 处）——操作者怒斥后截图自证：顶栏区域从屏幕顶到搜索框 221dp，完全违背「顶栏固定 54dp」。
- **定案理解**：顶栏行（状态栏下缘起 54dp）固定，**搜索框紧贴图标行下方（间距 0）**。
- 实施：`NtpContentShiftDown` 187 → **52dp**（32 + 52 + 2 = 搜索框顶 86dp = 图标行正下方）。
- 组装 **1.4.6-beta**（code 188）成功；装机 Success（12:12）。uiautomator 复测：搜索胶囊图标顶 94dp（卡片顶 86dp，间距 0）、快捷 312dp、资讯头 ≈583dp；图标行 32–86dp 未动。
- 里程表现在 **1.4.7 / 189**。教训：操作者的「间距/位置」一律以「距屏幕顶的距离」确认，禁用「A 与 B 之间的间距」歧义表述。
